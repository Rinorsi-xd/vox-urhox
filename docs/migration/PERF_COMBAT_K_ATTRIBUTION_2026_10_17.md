## Result

This capture does **not** demonstrate improved sustained combat FPS. The complete
controlled Web battle window contains 1,189 continuous complete frames over
45,136 ms: mean 37.961 ms (26.34 frames/s), P50 34 ms, P95 66 ms, P99 78 ms,
maximum 140 ms, and seven intervals above 80 ms. The roster began with eight
real vehicles and seven real AI drivers; actual combat produced 1,049 shots,
1,570 hits, 980 player damage and real structure loss (minimum 967 parts).

The result is one current-build attribution capture with production monitoring
enabled. It is not a matched before/after experiment. Earlier J numbers must
not be used to calculate a sustained-FPS benefit or regression without a matched
workload and observer comparison. Native loading and respawn improvements are
different scoped measurements.

were inserted, shifted individually or interpolated.

Inclusive parent/child numbers overlap and must not be added. Self time excludes
only instrumented children, and can still contain native calls, allocation,
automatic GC or scheduling pauses. Small per-method measurements use an integer
millisecond clock; totals across many calls are more useful than a single zero.

Fixed-step distribution is 180 frames with one step, 570 with two, 377 with
three, 58 with four, and four with five. Thus the battle repeatedly performs
multiple simulation steps per presented frame; this increases work per frame.
Changing the fixed-step contract is not justified by this report alone.

The three additional coarse observations average Finalize 0.209 ms/frame,
Context 0.071 ms/frame and Emit 0.052 ms/frame. Emit is inside Finalize. These
numbers do not measure all production monitor wrappers/allocations, and do not
prove an observer-free frame rate. The seven >80 ms frames have only 0-1 ms
Finalize, 0 ms Emit and 0-1 ms Context, so log emission is not the direct measured
long span for these particular spikes.

Four of seven spikes are directly attributed to `unit.Flush` elapsed time with
actual part removal. Current `CarUnit:Flush` performs graph/connectivity work,
detached-component debris generation, `Spec.Build` for the changed blueprint,
vehicle disposal/rebuild and state restoration. `unit.Build` is already a child
scope and does not account for most of the long Flush self spans. The next
targeted measurement should split this destructive path, especially
graph/connectivity, detached components and Spec.Build. The spawn-spec cache
cannot simply replace this rebuild: the blueprint has changed, so replaying the
original full vehicle specification would be incorrect.

The isolated 47 ms objective and 37 ms AI samples coincide with large reductions
in observed Lua heap (about 15.5 MiB and 14.9 MiB relative to the previous frame).
Some Flush spikes also coincide with heap reductions. This is an association,
not proof that automatic GC caused those spans. The `gcActive=false` and
`gcStepping=false` fields describe the project's explicit GC controller; they
do not prove that Lua's automatic collector did no work. No GC mode change,
forced collection or diagnosis by elimination is warranted here.
