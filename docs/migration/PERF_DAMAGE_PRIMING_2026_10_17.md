# 破坏重建：加载期炮管净空预热实验

日期：2026-10-17。状态：`EXPERIMENT_VERIFIED / SHIP_NOT_APPROVED`。

## 结论

本实验确认了一个具体问题：命中 `SpawnSpecCache` 后，新建的实际战车蓝图没有自己的 `TurretRange` 缓存，首次破坏时重新计算炮管净空，构成较大的 `CarUnit:Flush()` CPU 开销。

候选在加载时对实际蓝图预热，首次破坏的 Flush 平均从 **50.95 ms 降至 10.47 ms（-79.5%）**。但这不是总计算量优化：本样本加载计算累计 **+125.0%**，加载加三次破坏累计 **+31.4%**；第 2、3 次破坏的两轮平均还分别增加 **11.9%、24.3%**。候选仍出现 84/95 ms 的 Flush。

因此只确认“首伤冷缓存成本可以提前计算”，**不建议将本候选直接作为已完成优化合入生产**。需要继续处理重复计算和总成本，并在真实加载调度、完整 Web 对局中验收。不能据此承诺骁龙 845 / TapTap 持续 30 FPS。

- A/B 唯一不同文件：`scripts/combat/CarUnit.lua`。
- A SHA-256：`ec07f2c50496b7ce70b86116b6425bf6499d1914141686832818a79f04d8dba7`。
- B SHA-256：`4d16b0dfcb5364e6fd711db2e62d4d4cd6bf049c10f27d044a7e2b0eae4ba2f1`。
- 探针 SHA-256：`1331618ef9074a5063f057cc6cef15f343ac406788d504fe1c3ccc97abbd2f04`。

候选仅在 `cache:Get(source)` 命中、`spec.ok` 且存在加载 checkpoint 时执行：

```lua
TurretRange.For(self.bp,spec.rotorOf,function() checkpoint(.75) end)
```

同步重生没有 checkpoint，不额外预热；缓存未命中仍走原 `Spec.Build`；损坏后的 Flush 仍根据当前 `self.bp` 构建，未拿原始完整车辆 spec 替代损坏结构。

A/B 的 `TurretRange.lua` 都添加相同的只读缓存存在性钩子，记录在 `fixtureInstrumentation`；没有改动该模块的计算。该钩子仅用于实验副本，不是生产变更。

## 实际测试与有效性

主 agent 依次启动四个独立 Native 进程：A1、B1、B2、A2。每进程 8 批全新场景，每批 8 辆真实 K 蓝图，分别执行真实缓存 Prepare/Get、带 checkpoint 的 Spawn，再对每辆车连续执行 3 次非核心方块 Destroy/Flush，共 **64 次 Spawn、192 次破坏重建**。

使用真实 Vehicle、Bullet、Debris、CombatView 和视觉消费；自动 GC 保持开启，无强制 GC。场景为空，不含地图、AI、开火、音频和实际画面呈现。计时使用整数毫秒墙钟与 `os.clock`；方法包装和样本记录会引入观察成本。父子方法是包含关系，不能相加当作独占时间。

这里的 checkpoint 只验证数值、单调进度、retain 所有权并计数，**没有真实 coroutine 分帧等待**。因此加载表表示累积计算成本，不能当成用户加载页等待时间或最大连续冻结时间。64 辆累计数也不是“一场 8 车对局”的加载耗时。

独立分析实际检查：

- 4 次退出码均为 0；原始日志无 Native ERROR；每批释放检查通过。
- 768 条破坏行为记录、256 条加载记录、256 条初始元数据，纯 Lua 蓝图/spec/HP/事件及其他车辆状态精确一致。
- A 的实际蓝图缓存均为冷；B 均为热，且有预热 checkpoint。每批 cache hits 依次为 1..8、misses 为 0。
- 预先规定的原生门槛为每分量同时满足 **2 个 float32 ULP 与绝对数值差 `1e-4`**（各字段自身单位；位置对应 0.1 mm），位置欧氏偏移不超过 0.1 mm，数值余量 `1e-12`；该门槛在此次任何运行前冻结，不追认旧实验。
- 共检查 2,880 对原生状态、37,440 个分量；最大实际偏移 **0.0000019073486328125 m（约 1.91 微米）**。原始值完整保留，未四舍五入后比较。
- 独立离线候选检查 128 项通过；本报告复核了其真实 BP/Spec/Cache 路径、同步路径、miss 路径、retain、yield/close 和异常 Dispose 的覆盖边界。

审查期间曾发现探针对 `x/y/z/w` 表使用 `ipairs` 会零次检查，已在 **v2 冻结及所有本次 Native 运行之前**修复。v1 未运行；本报告不使用 v1 或旧 scalar 失败实验来放宽任何结果。

## 计算成本：包含不利结果

以下为 A1/A2 与 B1/B2 各自两轮平均，单位 ms，均是每进程累积值。

| 范围 | A 平均 | B 平均 | 变化 |
| --- | ---: | ---: | ---: |
| 缓存 Prepare，64 次 | 3516.0 | 4407.5 | +25.4% |
| Spawn，64 次 | 488.0 | 4599.5 | +842.5% |
| 加载 Prepare + Spawn | 4004.0 | 9007.0 | **+125.0%** |
| Flush，192 次 | 4226.5 | 1807.0 | -57.2% |
| 其中 TurretRange.For，192 次 | 3737.5 | 1187.5 | -68.2% |
| 加载 + Flush | 8230.5 | 10814.0 | **+31.4%** |
| 全部 setup + Flush | 9178.0 | 11959.0 | +30.3% |

Prepare 的实现并未因候选直接改写，但 B1 的 Prepare 明显更慢；这里只报告观测，不能将其全部归因于某一行预热代码。B1 的整体计算比 B2 慢，存在进程间波动；没有足够数据把后续破坏的回退断言为确定的算法退化或 GC 原因。

| 每次破坏 Flush 均值 | A | B | 变化 |
| --- | ---: | ---: | ---: |
| 第 1 次，每进程 64 条 | 50.95 | 10.47 | **-79.5%** |
| 第 2 次，每进程 64 条 | 7.95 | 8.90 | **+11.9%** |
| 第 3 次，每进程 64 条 | 7.13 | 8.87 | **+24.3%** |

首伤的方向在两次 B 中都成立；后续回退在 B1 更明显。B2 的第 2 次均值 7.34 ms 与 A 的 7.73/8.17 ms 接近，第 3 次 7.28 ms 与 A 的 7.05/7.22 ms 接近。不能只展示首伤收益，或以 B2 单次较好结果替换预先规定的 ABBA 平均。

## 尾部卡顿没有完全消失

P95 使用 nearest-rank `ceil(n*0.95)`，不插值；每行首伤有 64 个样本。

| 进程 | 首伤均值 | 首伤 P95 | 首伤最大 | 全部 192 次 Flush >80 ms |
| --- | ---: | ---: | ---: | ---: |
| A1 | 51.89 | 150 | 161 | 9 |
| B1 | 12.00 | 21 | 95 | 1 |
| B2 | 8.94 | 15 | 84 | 1 |
| A2 | 50.02 | 143 | 158 | 9 |

候选将本样本 >80 ms 的 Flush 从 18 条降至 2 条，但仍然存在，并且这不是整帧时长。不能据此宣布战斗卡顿全部解决。B1 最大 Flush 95 ms，而其最大 TurretRange.For 为 24 ms；B2 仍有 TurretRange.For 81 ms。剩余尖峰需分别追踪，不能统一归咎于 AI 或渲染。

## 后续决定与边界

本候选保持在 tools 隔离实验范围。下一步应验证能否在保留每辆实际蓝图独立缓存、损坏/修复/转子拥有关系正确性的前提下，减少完整 pristine 模板和实际蓝图重复计算，而不是再多算一次。任何新的缓存复用方案都需要纯数据等价、取消/释放验证及相同负载的原始时序对照。

进入生产前还需要真实加载器的分帧预算/取消测试、实际 Web 构建的加载到首伤以及后续破坏 P95/P99、长期内存和退出重进；最终目标仍是 TapTap 骁龙 845 真机持续对局与温升测试。此次没有提供完整战斗 FPS、Web 性能、移动端或真机通过证据。
