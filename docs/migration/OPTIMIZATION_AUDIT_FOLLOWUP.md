## 后续候选顺序与验收

1. **补足迁移版基线**：同一构建记录大厅、满配车改装、地图、战斗各自的帧时间、绘制量、GC、资源量，分开冷/热启动和持续运行。现有帧时间探针用于局外回归；常驻 Profiler 需另查引擎 API。
2. **Web 存档持久化**：先确认平台账号与 `clientCloud` 契约，再做存储适配器。验收刷新、退出重进、断网恢复、旧档导入和冲突；保留原车位与分享交互，不把会话内读写通过当成持久化通过。
3. **Shader 冷启动与纹理内存**：分别验证 Web/Mac 的 shader 录制预缓存，以及每类实际纹理格式/层级。已有 22.7s 冷编译失败记录；缓存运行通过不能替代首次编译测试。4096→2048、数组缩层/缩尺寸先做视觉 A/B，不能直接宣称无损。
4. **零件按需下载的剩余验收**：依赖门禁与三端浏览器流程已完成，见 `PART_MODEL_STREAMING.md`。继续做真实网络限速/失败恢复、所有零件冷访问和真机持续运行。不要再把 579 个模型阻塞启动当作当前事实。
5. **后处理、其余 GPU 特效、LOD/遮挡与物理**：先量占比，再独立优化。合并后处理必须固定机位/时间/曝光做画面 A/B；LOD 不破坏零件轮廓和关节；碰撞简化须保持驾驶、射击和相机行为。延迟渲染不作为当前 Web/手机默认方案。
6. **存档与预览生成**：量解析次数、GPU 读回峰值与额外大厅驻留，再决定缓存或编码格式。压缩 API 和 `string.pack` 必须在目标运行时验证，不能把文档声明当成可用性验收。

上述候选中，零件门禁及局外帧/批次/模型统计已有新证据，其余项仍待执行，不能把这份清单当作全部完成。先完成当前局外页面复刻收尾；教程、局内战斗操作和无尽模式仍不在本轮迁移范围。项目优化仍以 PC、20:9/16:9 横屏手机和 4:3 横屏平板为目标，不新增竖屏页面。

## 性能证据边界

Windows 浏览器模拟触控及原生移动质量档只证明对应配置可运行。M1 和真实手机的 30 分钟持续帧率、温度、内存、冷启动及多车压力尚未验收。现阶段不承诺帧率翻倍、稳定 60 FPS、冻结消失或总内存下降 40–50%；每项收益需要注明构建、设备、场景和采样范围。
